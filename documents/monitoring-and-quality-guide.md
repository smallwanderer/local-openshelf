# 품질 관리와 평가, 그리고 모니터링 가이드

Dotori는 거의 모든 요청마다 처리 시간을 측정하고, 문제가 생겼을 때 원인을 추적할 수 있는 고유번호(`trace_id`)를 남기며, 검색 품질을 직접 점검할 수 있는 여러 기능을 제공합니다. 이 문서는 이런 기능들이 어디에 있고 무엇을 보여주는지, 그리고 실제로 어떻게 쓰는지를 정리합니다.

아래 내용 대부분은 관리자(staff) 권한이 있어야 접근할 수 있으며, 개인 호스팅의 경우엔 기본적으로 본인만 해당 권한을 가지게 됩니다.

## 1. 운영 현황 페이지

`/workspace/operations/`에서 서버 전체의 현재 상태와 최근 처리 성능을 한 화면에서 확인합니다. 사이드바의 **운영 요약** 메뉴는 관리자 계정에만 표시되며, 일반 계정으로 URL에 직접 접근하면 권한 안내만 표시됩니다.

이 화면이 보여주는 것은 계정별 통계가 아니라 **서버 전체 통계**입니다. 검색어·질문 원문·문서 본문은 어떤 항목에도 노출되지 않습니다.

### 1.1 화면 구성

| 영역 | 내용 |
|---|---|
| 즉시 상태 | 웹 API·DB·임베딩·RAG 런타임이 지금 응답하는지 (정상/점검 필요/미설정) |
| 기간 요약 | 조회 기간(1시간/24시간/7일)을 골라 업로드·검색·RAG의 건수, 성공률, 평균·최대 소요시간, 실패·시간 초과 건수를 확인 |
| 파이프라인 성능 | 업로드·파일 작업·파싱·임베딩·검색·RAG 답변 단계별로 세부 소요시간(예: 쿼리 임베딩, 벡터 쿼리, 재정렬, LLM 첫 토큰까지 시간 등)을 펼쳐서 확인 |
| 처리 대기와 실패 | 파싱·임베딩이 밀려 있는 문서/청크 수, 오래 멈춰 있는 항목 수 |
| 느린 작업과 최근 실패 | 선택 기간에서 가장 오래 걸린 작업과 최근 실패한 작업 목록 |
| 자원 스냅샷 | DB 연결 수, uploads/logs/config 볼륨의 남은 디스크 용량. **지금 수집** 버튼으로 즉시 갱신 가능 |
| 현재 서버 설정 | 운영 모드, 웹 worker 수, 요청 제한 시간, 문서 처리 worker 동시성, 배포된 commit 등 읽기 전용 정보 |

숫자가 없는 항목은 `0`이 아니라 "측정값 없음"으로 구분해서 표시됩니다. 과거에 기록되지 않은 값을 0으로 오해하지 않도록 설계된 부분이므로, 빈 값과 실제 0을 혼동하지 마세요.

### 1.2 느린 작업·실패 항목에서 원인 조사하기

"느린 작업과 최근 실패" 목록에서 항목을 클릭하면 우측에 **작업 추적(trace)** 패널이 열립니다. 여기서 확인할 수 있는 것:

- 해당 요청에 연결된 파이프라인 단계들과 각 단계의 상태·소요시간
- 검색과 RAG가 이어진 요청이라면 두 작업을 한 흐름으로 표시
- 전체 `trace_id`와 복사 버튼 — 이 값으로 로그 파일을 뒤져 더 자세한 원인을 확인할 수 있습니다 (2장 참고)

### 1.3 아직 자리만 있는 메뉴

사이드바에는 **AI 설정·정확도**, **Trace 탐색** 메뉴도 함께 보이지만, 이 두 화면은 아직 안내 문구만 표시되는 자리표시자입니다(향후 예정 표시가 붙어 있습니다). 임의의 `trace_id`를 직접 입력해 조회하는 기능이나, 임베딩·RAG 정확도를 화면에서 바로 확인하는 기능은 아직 이 경로로는 연결되어 있지 않습니다 — 지금은 느린/실패 항목을 클릭해서 얻는 `trace_id`, 또는 로그·DB를 직접 조회해 얻는 값으로 3장·4장의 방법을 사용해야 합니다.

## 2. trace_id로 문제 추적하기

`trace_id`는 요청 하나를 관통하는 고유번호입니다. Dotori 안에는 두 종류의 기록이 있습니다.

- **성능 기록**(위 대시보드가 보여주는 숫자): "얼마나 걸렸는가"에 답합니다.
- **애플리케이션 로그**(3장): "이 요청에 무슨 일이 있었는가"에 답합니다.

실패·시간 초과 같은 값은 실패했다는 사실만 알려줄 뿐 원인을 담지 않으므로, 실제 원인을 알려면 같은 `trace_id`로 로그를 찾아봐야 합니다. 반대로 에러 로그를 먼저 봤다면 같은 `trace_id`로 성능 기록을 찾아 정량적 맥락(어느 구간이 느렸는지, 재시도 횟수 등)을 확인할 수 있습니다.

trace는 두 종류로 나뉩니다.

- **적재 trace**: 문서 하나가 업로드되어 파싱되고 임베딩되기까지의 흐름을 잇습니다.
- **질의 trace**: 검색부터 답변 생성까지를 잇습니다 (한 요청 안에서 동기로 처리되므로 자연히 하나의 흐름입니다).

업로드와 검색은 서로 독립된 이벤트라 하나의 trace로 이어지지 않습니다.

`trace_id`를 얻는 방법은 두 가지입니다.

1. 운영 현황 페이지에서 느린/실패 작업을 클릭해 trace 패널에서 복사 (1.2절)
2. Django admin(`/admin/`)에서 `SearchJob`/`RAGJob`/`DocumentParseResult` 등의 `performance_metrics` 필드 안에서 확인

값을 얻었다면 로그 파일에서 검색합니다.

```bash
grep <trace_id> data/logs/*.log
```

## 3. 로그 파일 훑어보기

`app`과 각 executor는 로그를 서비스별로 나눠 씁니다(같은 파일에 동시에 쓰면 로그 줄이 섞일 수 있어서 분리했습니다). 위치는 `data/logs/`이며 파일당 최대 10MB, 백업 5개로 자동 로테이션됩니다.

| 파일 | 내용 |
|---|---|
| `operations.<service>.log` | Django/Celery 프레임워크 자체 로그와 그 외 나머지 |
| `document_ai.<service>.log` | 파싱→임베딩→검색→RAG 파이프라인의 진행 상황 서술 로그 (큐 시작/완료, 실패 원인 등) |
| `files.<service>.log` | 업로드·폴더 생성·이름변경·이동·삭제, 동기화(sync) API 로그 |
| `db_span.<service>.log` | 계측 대상 함수(검색·RAG·파싱·임베딩) 안에서 실행된 SQL 문 단위 기록. 어떤 쿼리가 몇 번 실행됐는지 확인할 수 있으며, **바인딩 파라미터 값(검색어·문서 내용 등)은 절대 남기지 않습니다** |

모든 로그 줄에는 같은 포맷으로 `trace_id`가 찍힙니다. `trace_id`가 없는 로그 줄은 `-`로 표시되며, 이는 요청과 무관한 백그라운드 동작이거나 아직 trace가 전파되지 않은 경로라는 뜻입니다.

파일을 직접 열어보거나, 컨테이너 안에서 실시간으로 볼 수 있습니다.

```bash
docker compose exec app tail -f /data/logs/document_ai.app.log
```

운영 현황 페이지는 로그 본문을 브라우저에 직접 노출하지 않습니다(경로 조작이나 민감정보 노출 위험 때문에 의도적으로 뺐습니다) — trace 패널이 제공하는 값과 위 grep 명령을 조합해서 조사하세요.

## 4. 검색 품질을 직접 점검하기

운영 현황 페이지는 "얼마나 빠른가"는 보여주지만 "검색 결과가 얼마나 정확한가"는 보여주지 않습니다. 검색 품질은 별도 관리 명령으로 직접 점검합니다.

### 4.1 evaluate_retrieval — 검색 정확도 측정

질문과 정답 문서를 짝지은 데이터셋을 준비하면 `HitRate@1`, `HitRate@K`, `MRR@K`를 계산해줍니다.

```bash
docker compose exec -T app python manage.py evaluate_retrieval --dataset /path/to/dataset.json --top-k 5
```

데이터셋은 아래와 같은 JSON 배열입니다. `expected_node_ids`에는 정답으로 인정할 문서/폴더의 UID를 넣습니다.

```json
[
  { "query": "환불 정책이 뭐야?", "expected_node_ids": ["<node-uid>"] }
]
```

출력되는 값의 의미:

| 값 | 의미 |
|---|---|
| `hit_rate_at_1` | 검색 결과의 첫 문서가 정답 중 하나인 질의의 비율 |
| `hit_rate_at_k` | 상위 K개 결과 안에 정답이 하나라도 포함된 질의의 비율 |
| `mrr_at_k` | 정답이 처음 등장한 순위의 역수를 평균한 값 (순위가 높을수록 1에 가까움) |

> [!CAUTION]
> 이 명령은 결과를 stdout에만 출력하고 저장하지 않습니다. 또한 실제 검색 API가 쓰는 랭킹 로직(문서별 후보 제한, 길이 패널티, contextual compression 등)을 그대로 재현하지 않는 별도의 단순화된 랭킹으로 채점합니다. 따라서 여기서 나온 수치를 실제 서비스 검색 품질의 공식 기준값으로 취급하지 마세요 — 설정 변경 전후를 상대 비교하는 용도로 쓰는 것이 안전합니다.

### 4.2 부하 상태에서도 버티는지 점검

소수의 동시 요청(팀 사용 기준 2~5건 수준)에서 검색·RAG API가 안정적으로 응답하는지 확인하는 스크립트입니다. 로그인 세션의 Cookie/CSRF 값이 필요합니다.

```bash
python3 scripts/check_search_load.py --cookie '...' --requests 5 --concurrency 3
python3 scripts/check_rag_stream.py --cookie '...' --csrf-token '...' --requests 3 --concurrency 1
```

결과는 화면(stdout)에만 출력되며 별도로 저장되지 않습니다. 대용량 처리량 벤치마크가 아니라, "이 정도 동시 사용자에서 깨지지 않는가"를 확인하는 용도입니다.

### 4.3 그 밖의 성능 확인 도구

RAG 답변 생성 쪽 동시성을 실측 데이터로 조정하고 싶다면 [운영 가이드](./operation-guide.md#llm-운용-동시성-calibration)의 calibration 스크립트를, 요청 단위 성능 수치를 직접 집계하고 싶다면 [운영 가이드](./operation-guide.md#성능-지표와-자원-확인)를 참고하세요.

## 5. 알아두면 좋은 한계

이 시스템의 계측·평가 기능은 팀 사용(10명 이하, 하루 수백 건 이하) 규모를 전제로 의도적으로 단순화되어 있습니다. 아래 항목이 없는 것은 미완성이 아니라 이 규모에서는 비용 대비 신호가 빈약하다고 판단해 만들지 않은 것입니다.

- **percentile(p50/p95/p99) 없음**: 표본이 작으면 p99는 사실상 "가장 느렸던 한두 건"과 다르지 않습니다. 평균·최댓값·건수로 충분하다고 보고 있습니다.
- **컨테이너별 CPU/RAM/GPU 사용률 없음**: 이 값을 얻으려면 호스트 도커 소켓 접근이 필요한데, 읽기 전용 마운트로도 도커 엔진 API 전체가 열리는 보안 위험이 기능 가치보다 크다고 판단해 만들지 않았습니다. 필요하면 호스트에서 `docker stats`를 직접 실행하세요.
- **RAG 동시 실행·거부 횟수 집계 없음**: 아직 영속 집계 계약이 없어 운영 현황 페이지에는 "수집되지 않음"으로 표시됩니다.
- **검색 품질의 공식 기준선 없음**: `evaluate_retrieval`이 계산하는 수치는 개발용 탐색 결과이며, 운영 검색 경로와 정확히 같은 방식으로 채점한 반복 가능한 기준선은 아직 등록되어 있지 않습니다.
- **자동 보존정책 없음**: 성능 기록과 로그 모두 예상 데이터량이 작다는 전제로 자동 삭제 없이 쌓입니다(로그는 로테이션 캡으로만 상한). 사용 규모가 크게 늘어나면 이 전제를 다시 검토해야 합니다.
